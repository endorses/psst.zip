# Security, abuse prevention and optional link limits

## Status and scope

Implementation in progress. The initial request/cleanup, proxy/authentication admission and recipient-safety changes are being verified. The private-inbox protocol, operator budgets, second factors, response controls and remaining client work are not complete. Do not treat this intermediate worktree as a security-hardened public release.

Protect self-hosted operators and recipients from confidentiality failures, resource exhaustion, unexpected traffic costs, compromised accounts and malicious submissions. Include optional per-link download/receive limits across web, Android and iOS, including sending through the iOS share extension. Preserve straightforward default workflows, public standalone download links, public receive submission, administrator-only management accounts, chunked encryption, configurable maximum file size and delivery acknowledgements. A public receive link grants submission access, not permission to read other submissions.

This expands and replaces `per-link-download-and-receive-limits.md`. The preceding assessment was a read-only source review, not a penetration test or completed cryptographic audit. Findings below are implementation targets; none are claimed fixed. The existing running development deployment remains unchanged until a compatible implementation is ready for its delivery checks.

This builds on [download acknowledgements](download-acknowledgements.md), [mobile navigation and scanning](mobile-navigation-scanning-and-branding.md), and [administration and traffic accounting](administration-dashboard-traffic-and-ux.md).

## Agreed behavior

| Link    | Optional control           | Meaning                                                                                 |
| ------- | -------------------------- | --------------------------------------------------------------------------------------- |
| Send    | Maximum downloads per file | Every file independently permits up to N download attempts across all recipients.       |
| Receive | Maximum files accepted     | The link permits up to N file upload allocations across all upload batches and senders. |

Both controls are disabled by default. Disabled means no user-selected limit; expiry, server-wide quotas and rate limits still apply. Limits are fixed at creation for this iteration. Owners can revoke a link or create a replacement; changing or replenishing an existing allowance is outside scope.

A send limit of 2 on a three-file transfer permits two attempts for each file. Downloading all files as a ZIP consumes one attempt for each file fetched from the server. Building or saving an archive from already downloaded local data does not consume another attempt.

A download attempt counts when the server authorizes a file response, before streaming its contents. Interrupted responses and fresh retries consume attempts. Opening the link, scanning its QR code, reading metadata or the encrypted manifest, and submitting a delivery acknowledgement do not. Successful receipt acknowledgements remain a separate delivery signal; they must not control quota enforcement because a hostile client can withhold them.

A receive allowance is reserved before accepting a new file body. Resuming the same upload does not consume another file allowance. A newly allocated replacement upload does. Incomplete, abandoned and zero-byte allocations also consume an allowance; deleting a child transfer does not restore it. This prevents repeated create/upload/delete cycles from bypassing the limit. The UI must explain this briefly rather than claiming that only successfully received files count.

These are limits on file access and upload allocations, not unique-person counts or an exact billable traffic cap. A recipient can redistribute saved copies, and control/manifest requests still generate traffic. Existing byte budgets and request limits remain necessary. The existing administrator traffic allowance remains a monitoring setting. This plan adds a separate, explicitly enabled enforcement budget; configuring a chart allowance must not silently enable blocking.

## Current implementation and entry points

The backend already accepts `max_downloads` when creating a transfer. `ReserveFileDownload` atomically enforces that limit independently for each file; the transfer's aggregate `download_count` is the minimum across its files. Do not present that aggregate as every file's remaining allowance. The current GET streams a whole encrypted blob; encryption frames within that stream do not create additional download attempts.

Receive links already have cumulative operator-controlled child-transfer and byte budgets. `CreateFileWithQuota` reserves declared bytes transactionally before inserting the upload record. There is no creator-selected total file allowance yet. Mobile receive screens currently create a link on entry; creation must become explicit so the user can choose limits first.

## Threat model, priorities and policy precedence

Assume an attacker can know a public link, share it, call APIs directly, use concurrent/slow requests, hold a compromised regular account, and operate a hostile server whose QR code a recipient scans. Client-side validation, authenticated encryption and optional link controls do not replace server enforcement. Encryption proves integrity under a key, not that a sender is trustworthy or a file is harmless.

| Priority | Finding or risk                                                                                | Release expectation                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| P0       | Shared receive key plus public child listing/read endpoints exposes other senders' files       | Private receive inbox with both authorization and cryptographic sender separation before promoting use with strangers |
| P0       | Unbounded creation JSON, slow request locks, blocked cleanup and uncapped live subscriptions   | Bound memory, connection lifetime/concurrency and cleanup work before recommending Internet exposure                  |
| P0       | No account/global storage budget or maximum standalone retention                               | Enforced finite defaults and a disk reserve independent of optional link limits                                       |
| P1       | Repeated manifest/file traffic can exceed monitoring allowance                                 | Separate enforceable payload budget, bandwidth and concurrency controls, clearly distinguished from provider billing  |
| P1       | Proxy-shared login throttling, inconsistent client-IP trust, administrator compromise          | Trusted-proxy handling, layered throttling and administrator second-factor support                                    |
| P1       | Malicious content, inability to quickly halt existing public links, unsafe deployment defaults | Operator response controls, minimal audit trail and deployment hardening                                              |
| P1       | Malicious scanned server consumes device storage/data; deceptive filenames                     | Recipient preflight and consistent filename safety on web and mobile                                                  |

Authorization and explicit revocation/suspension take precedence over allowances. Global and account restrictions take precedence over per-link settings. Per-link controls may only reduce access. An exhausted receive file count still permits its already allocated uploads to finish, unless a higher-priority emergency/traffic/storage restriction blocks them. Administrative sign-in, inspection, revocation, cleanup and recovery must remain reachable while public file traffic is paused.

## 1. Private receive inboxes

Evidence: `getSlot` publicly enumerates child transfers, slot events disclose new IDs, and child manifests/files are publicly readable. `UploadJob` imports the receive URL's symmetric key and uses it for every submission. Anyone holding that URL can currently decrypt other senders' uploads. Removing UI links alone cannot fix this.

- [ ] Separate public **submission availability** from authenticated **inbox listing, events and content retrieval**. Guests receive only expiry/availability and effective upload allowances needed to submit. Do not expose child IDs or activity history through metadata, SSE, errors or alternate endpoints.
- [ ] Require the regular account owning the inbox for reading its child transfer metadata, manifests, files and delivery-state operations. Apply guards to every route, including direct child URLs and alternate file methods; do not rely on secret IDs or hide-only navigation. Keep standalone send links publicly downloadable and administrator operational metadata/revocation available without plaintext/key access.
- [ ] Keep invited uploader capabilities scoped to creating/writing their own submission. Prevent those capabilities from listing or reading other children, forging their delivery status or consuming their download allowance. Preserve upload resume without granting inbox read authority.
- [ ] Introduce a versioned receive protocol using the receiver's public encryption key, a fresh random symmetric key per submission, and a standard authenticated key-wrapping/encryption construction. The private recipient key stays on owner devices. Select maintained cryptographic libraries interoperable across web/Kotlin/Swift, document the precise suite, and have the protocol reviewed before implementation is declared complete; do not invent custom cryptographic primitives.
- [ ] Bind the intended recipient public key or its fingerprint to the shared receive capability so an untrusted server cannot silently substitute a recipient key. Authenticate protocol version, slot identity and submission context in the envelope. Keep private keys and decryption material out of API requests, logs and analytics.
- [ ] Version the receive URL/QR and manifest envelope explicitly. Reject unsupported versions instead of falling back to the shared-key scheme. Preserve standalone download links. Update browser guests, native guest uploads, owner download pipelines and applicable share-extension code together.
- [ ] Store owner private keys with existing account/server-scoped key storage and History; missing-key devices may manage metadata/revoke but cannot decrypt. Pairing must not silently export inbox private keys. Explain device/key availability without introducing unsupported synchronization.
- [ ] Restrict reads of existing shared-key inboxes immediately and stop accepting new submissions on those legacy links. Let authorized owners retrieve existing data and create replacement links. Do not claim migration can undo earlier access by other holders or automatically delete existing user data. Document the compatibility break and safe deployment order.
- [ ] Test two unrelated senders, a malicious sender who knows the full upload URL, unrelated logged-in users, administrators, owner devices without keys, revoked sessions and changed ownership context. Verify denial of direct reads/listings/events and inability to decrypt a different sender's test ciphertext even when its envelope is supplied outside the API. Document remaining trust in the delivered browser application.

## 2. Bounded requests, connections and cleanup

Evidence: `api/helpers.go` decodes creation JSON without a size limit; slot-child creation takes a shared lock before reading its body; streaming mutations can hold one of 256 striped locks; `cmd/server/main.go` has zero read/write timeouts. The sequential cleanup worker can wait behind such a request. Each public slot-event subscription currently polls SQLite once a second.

- [ ] Apply small explicit request-body limits before decoding control JSON, with strict validation and bounded headers/metadata. Limit manifest size separately and consistently with client support. Reject malformed/oversized requests without creating resources or retaining large buffers.
- [ ] Configure header, control-body and idle-stream deadlines at the application/proxy boundaries. Use progress-based upload/download deadlines so slow legitimate large files can complete while stalled peers cannot keep work indefinitely. Do not apply one short fixed total timeout to all file transfers.
- [ ] Parse bounded control bodies before acquiring resource locks. Bound lock acquisition/cancellation, avoid unrelated-resource starvation from striped locks, and shorten critical sections around stream IO while preserving upload offset, completion, deletion and quota correctness.
- [ ] Ensure one stalled/busy resource cannot block the whole cleanup sweep. Use bounded work, skip/retry semantics and observable cleanup backlog/oldest-pending age. Cancel expired or revoked in-flight work and reconcile partial disk/database state after crashes.
- [ ] Limit active uploads, downloads, queued operations and event streams globally, per account, per link and per resolved client address where appropriate. Enforce caps at acquisition, release on every error/cancellation path, bound waiting queues and return useful retry information. Account for HTTP multiplexing rather than counting TCP connections alone.
- [ ] Authenticate inbox event streams, limit their lifetime/idle behavior and share lifecycle polling per inbox instead of per subscriber. Handle slow subscribers with bounded queues and disconnect them when necessary.
- [ ] Add a bounded global admission guard before expensive authentication/database/body work, alongside endpoint-specific rate limits. Bound limiter cardinality and expire state without creating a memory exhaustion avenue through many client identities.
- [ ] Test oversized control bodies, slowly delivered bodies, disconnects, stalled readers, concurrent finalization/deletion, repeated SSE connections and expiry during upload using disposable data and bounded test loads. Verify unrelated transfers, administrative access and cleanup continue functioning; do not run exhaustion tests against the live development service.

## 3. Operator storage and retention budgets

Per-link allowances must not be the sole protection against a compromised account creating many new links. Limits include standalone transfers, receive submissions attributed to the receive owner, unfinished uploads, manifests, object/row counts and operational overhead.

- [ ] Add persistent administrator settings for total server storage, per-account storage, active files/transfers/receive links, maximum standalone/receive retention and pending-upload lifetime. Ship finite documented defaults; derive effective admission from both configured quotas and actual capacity. Publish and test the numeric default profile before release, including small-disk installations, rather than leaving deployment values silently unlimited.
- [ ] Maintain a configurable free-space reserve on the relevant data/database volumes. Check capacity at allocation and during streaming and stop safely before exhausting the host. Explain that external processes can consume space after admission; enforce write bounds and handle ENOSPC without corruption.
- [ ] Reserve bytes/objects atomically across all relevant scopes before accepting content, including encrypted overhead. Count manifests and their replacement deltas. Prevent parallel uploads through different links from overcommitting account/global budgets.
- [ ] Separate **current occupied/reserved capacity**, which can be released after verified deletion, from **cumulative per-link abuse allowances**, which do not refill on deletion. Count open-but-unlinked data until ongoing streams close when estimating disk pressure; reconcile counters conservatively after restart.
- [ ] Bound maximum retention for standalone transfers as well as slots; reject overflow and unreasonable lifetime values. Enforce limits through direct APIs and inherit/clamp child expiry to its parent. Introduce a bounded unfinished-upload lifetime so abandoned allocations cannot persist indefinitely.
- [ ] Define safe changes to limits on an already populated server: lowering a quota blocks new allocations while preserving existing data and admin recovery, rather than silently deleting user files. Show used, reserved, available and stale/reconciliation states; advertise effective upload limits to clients.
- [ ] Paginate/bound history and administrator resource queries so many tiny/empty resources cannot turn list endpoints into unbounded memory or database work. Bound retained traffic/audit records and account/session metadata as part of database capacity planning.
- [ ] Test concurrent allocation, tiny and empty files, large manifests, account quota attribution, disk pressure, deletion failures, restarts, quota reductions and counter reconstruction. Keep cleanup usable when the database/storage is nearly full.

## 4. Enforceable traffic protection

The current chart allowance remains monitoring-only. File-attempt limits do not bound manifest downloads, aborted uploads, repeated manifest writes or other payload operations. Add a separate operator policy with clear consequences.

- [ ] Add an explicit **Enforce transfer traffic budget** setting with byte allowance, outbound/combined basis and billing-cycle rules. Reuse the existing UTC cycle semantics without rewriting historical measurements. Keep monitoring and enforcement independently visible and default enforcement off until an operator supplies a budget.
- [ ] Enforce a durable global budget and configurable account budgets on actual encrypted payload traffic, including manifests, retries and partial/failed operations. Attribute public traffic to the resource owner. Keep resource reservations distinct from measured traffic and do not refund measured bytes on deletion.
- [ ] Reserve/lease bounded byte allowances before stream IO and settle actual usage, with atomic concurrency handling, bounded buffering, restart recovery and conservative behavior on accounting failure. Define and test any maximum in-flight overshoot; chart refresh intervals or post-response accounting cannot serve as admission control.
- [ ] Stop or pause payload streams when the enforcement budget is reached, release unused reservations safely and return stable errors/retry-cycle information. Do not automatically retry requests that would burn additional download attempts. Preserve completed local files and explicit retry/resume behavior.
- [ ] Add configurable upload/download bandwidth and concurrent-stream limits with a documented finite concurrency default. Include manifest endpoints in byte/rate enforcement even though reading a manifest does not consume a file-download attempt.
- [ ] Keep administration, budget changes, sign-in, revocation, health and cleanup available during a stop; tightly rate-limit their control traffic independently. Show clear paused/budget-exhausted states on public links and all clients.
- [ ] Explain the measurement boundary: application transfer payload is not a provider bill, TLS/HTTP/proxy overhead, rejected network traffic, static assets, backups and network-level DDoS may still incur costs. Document provider firewalls/DDoS or spend controls as complementary protections without promising application-level billing guarantees.
- [ ] Verify concurrent final bytes, manifest repetition, cycle rollover, in-flight rollover policy, process crash, quota changes and degraded accounting. Demonstrate that a request lacking a receipt or ending early still spends the bytes transferred.

## 5. Authentication, proxy trust and administrator protection

The current login limiter uses the immediate peer address, so all users behind Caddy share one attempt bucket. The general limiter instead trusts arbitrary `X-Forwarded-For`. These approaches must be replaced by a consistent, tested trust boundary.

- [ ] Implement one canonical client-address resolver based on the socket peer and an explicit trusted-proxy allowlist. Parse/normalize the trusted chain consistently, including IPv6; ignore forwarded headers from untrusted peers. Never default to trusting all Internet addresses. Provide tested direct, bundled Caddy and external-proxy configuration examples.
- [ ] Combine client-address and normalized-account login throttles with a global expensive-password-work concurrency cap. Distinguish login/pairing limits appropriately, keep error messages non-enumerating, and avoid permanent account lockouts or shared proxy buckets that let one attacker deny everyone service. Bound tracking memory and document distributed-attack limits.
- [ ] Preserve HttpOnly/Secure/SameSite cookies, same-origin mutation checks, hashed session/pairing secrets, mandatory temporary-password replacement and single-use expiring pairing codes. Add focused regression checks while changing admission/auth ordering.
- [ ] Add administrator second-factor support using maintained implementations, choosing and recording passkeys/WebAuthn or password-plus-TOTP before implementation. Prefer passkeys where deployment/origin compatibility permits; ensure a complete enrollment, verification, recovery and revocation flow rather than an unenforced UI switch. Surface incomplete setup prominently without silently locking existing administrators out during upgrade.
- [ ] Require recent authentication for high-impact actions such as changing authentication factors, operator budgets, emergency-stop policy and broad account revocation. Bound recovery attempts, hash recovery codes, make them single-use, and provide a documented local-operator recovery path that does not depend on an email service.
- [ ] Keep normal password login and applicable native account flows compatible. Admins remain administration-only, and neither pairing nor the device-token login route may bypass an enabled second factor. If second factors are exposed to regular accounts, implement Android/iOS/share-extension support in the same delivery.
- [ ] Test spoofed forwarded headers, real trusted proxy chains, shared NAT clients, distributed low-rate attempts, login-flood responsiveness, stolen/revoked sessions and factor recovery. Administrator access must remain practical during public-transfer suspension.

## 6. Malicious content, incident response and deployment hardening

End-to-end encryption prevents server inspection of honest ciphertext. A custom client can also upload arbitrary bytes; the server cannot promise all stored material is well-formed encrypted content. Do not introduce a decryption backdoor or claim server-side antivirus certifies these transfers as safe.

- [ ] Add administrator actions to suspend an account, revoke its sessions/pairings, revoke all its transfer/receive capabilities, stop active transfer IO and schedule cleanup. Make the scope explicit before confirmation; distinguish disabling future sign-in from shutting down existing public links. Resolve active-stream races and verify revoked capabilities cannot restart work.
- [ ] Add a persistent emergency **Pause public transfers** control that blocks public payload upload/download and cancels relevant in-flight work while preserving admin/recovery access. Provide a documented local control path if the web UI is unavailable; resumption must be deliberate and must not resurrect explicitly revoked links.
- [ ] Extend resource management with owner, type, creation/expiry, byte/object counts and relevant abuse events so an operator can identify and revoke a reported resource without plaintext. Bound/paginate results and support targeted cleanup with visible failures.
- [ ] Add an optional administrator-configured abuse contact/reporting path. Reports identify the instance and opaque resource ID without sending the decryption fragment, private keys or file content. Rate-limit, size-limit and retain reports conservatively; do not make the reporting endpoint a new spam/open-mail relay or accept arbitrary attachment uploads. A contact-only deployment may omit an in-app submission endpoint.
- [ ] Keep a minimal bounded security audit trail for administrative changes, suspicious authentication patterns, suspensions and revocations. Redact authorization headers, cookies, pairing codes, key fragments and sensitive query values; avoid logging request bodies, filenames or decrypted metadata. State retention and access policy and rotate application/container logs.
- [ ] Harden supplied deployment configuration: private backend networking, explicit trusted HTTPS setup, prominent opt-in development HTTP, non-root execution where supported, least capabilities, no-new-privileges, restricted writable paths, process/memory/CPU limits and tested restart behavior. Keep storage/database/key material out of the static web root and avoid exposing diagnostic/admin ports publicly.
- [ ] Add a tested Content Security Policy compatible with compiled assets, theme initialization, local QR scanning, blob downloads, workers and intentional external-server scan behavior. Preserve nosniff, frame denial, no-referrer and camera restrictions. Treat CSP as defense in depth, not evidence that an existing XSS has been found.
- [ ] Document supported dependency/base-image update and vulnerability-check workflows, signed/reproducible release verification where available, backups/restores and safe credential handling. Ensure updates do not reset operator budgets/proxy policy. Describe what restored metadata/key material can and cannot recover without promising server access to plaintext.
- [ ] Align security claims throughout UI/README: trusted HTTPS and trustworthy client software remain necessary, browser-delivered JavaScript depends on its serving origin, encryption does not prove sender identity or file safety, and operators need a way to respond to abuse. Do not imply encryption removes hosting-provider obligations or guarantees legal immunity.
- [ ] Test emergency stop/revoke during concurrent upload/download, account suspension with existing public links, restart during cleanup, tampered report fields, secret redaction, bounded logs, recovery access and both bundled/external proxy setups using isolated deployment data.

## 7. Recipient safeguards for hostile links and files

Native scan-to-download currently starts streaming after a manifest is read; the format supports up to 100 files with very large per-file ceilings. A hostile external server is not constrained by the recipient's own configured server upload limit. Web filenames currently retain bidirectional controls that native filename sanitization already strips.

- [ ] Validate the complete manifest before file retrieval: bound manifest bytes, count, per-file/aggregate size with overflow-safe arithmetic, framing overhead and expected resource IDs. Do not trust declared sizes alone; enforce cumulative actual bytes during download/decryption and reject mismatches before publishing files.
- [ ] Add total-download preflight, available-device-space checks and a free-space reserve on Android/iOS and applicable browser save paths. Account for temporary copies and ZIP overhead. Use conservative behavior and a clear message where the browser cannot reliably inspect destination free space.
- [ ] Preserve immediate receiving for small valid transfers while requiring explicit confirmation above a documented aggregate-size threshold or a configured metered-data limit. Show the destination server, file count and total size before consent; changing to a materially different manifest invalidates prior consent. Choose and test the numeric threshold as part of the release default profile.
- [ ] Bound automatic retries and download-job concurrency; support prompt cancellation and safe temporary-file cleanup. Resume only verified partial/local state, preserve already saved files and avoid repeatedly fetching a malicious oversized response. Test low disk, background/foreground and process termination.
- [ ] Apply consistent safe display/save naming across web, Android and iOS, including path separators, control/bidirectional characters, misleading extensions, duplicate/colliding names and ZIP entries. Preserve meaningful filenames without allowing traversal, silent overwrites or extension spoofing through hidden direction controls.
- [ ] Keep files inert until the user chooses Open/Share. Do not auto-execute, install, expand archives or embed active HTML/SVG content in the service origin. Treat MIME values and filenames as untrusted, and keep native URI grants limited to the selected file.
- [ ] Preserve isolated anonymous clients for scanned standalone links, no credential forwarding to a different origin, redirect/TLS restrictions, visible server identity and explicit pairing confirmation. Never send fragments to server-side link scanners, analytics or abuse reports.
- [ ] Verify legitimate and hostile manifests, large totals, deceptive names, mismatched lengths, cancellation, unsupported file types, direct/QR/pasted links and external-server behavior across all clients. Confirm no new credential/key leakage or raw HTML rendering is introduced.

## 8. Per-link API contract and persistence

- [ ] Keep `max_downloads` on authenticated transfer creation and add `max_files` on authenticated receive-link creation. Omitted or zero means no user-selected cap. Accept only nonnegative integers up to 2,147,483,647; reject negative, fractional, string, overflowing and malformed values with a stable validation error. Preserve existing empty-body creation requests as the unlimited default.
- [ ] Validate JSON strictly enough that malformed requests cannot silently become unlimited links. Specify and test handling of null values, unknown fields and trailing JSON consistently for both creation endpoints.
- [ ] Add additive, restart-safe slot columns for `max_files` and cumulative `reserved_files`. Existing links retain unlimited user-selected file counts. Backfill known allocations from existing file rows where possible; do not claim to reconstruct deleted historical allocations. Existing links cannot acquire a new limit in this iteration.
- [ ] Return configured limits and usage through public standalone-transfer metadata and authorized owner History/detail responses. Public receive availability exposes only the minimal policy needed for submission, not child IDs, filenames, activity history or existing file metadata. Include per-file download attempts/remaining allowance keyed by opaque file ID, without plaintext filenames or keys. Preserve compatible standalone/owner response fields and distinguish an absent counter from a known zero. Compatibility must not preserve public inbox disclosures removed by section 1.
- [ ] Return owner receive counts separately: accepted/completed files, cumulative allocated file allowances and remaining allowance. Do not label reservations as successfully received files. Expose enough information for upload clients to preflight selections while keeping server allocation authoritative.
- [ ] Introduce stable machine-readable limit errors, distinguishing exhausted file downloads, receive file allowance, existing byte/batch quotas, expiry and revocation. Preserve meaningful HTTP statuses and compatible human-readable messages.
- [ ] Update shared/web request and response models with backward-compatible defaults for additive fields. If capability/version detection is needed for older servers, prevent clients from silently claiming that an unsupported selected limit is enforced; refuse limited creation with a clear update requirement.

## 9. Per-link enforcement and resource lifecycle

- [ ] Reuse and verify existing atomic per-file download reservation rather than adding a second counter. Reserve only after verifying the resource and opening its payload; a missing payload must not consume an allowance. Concurrent requests cannot exceed N.
- [ ] Preserve one attempt per file response, including a fresh retry or a GET with a Range header under current whole-response behavior. Do not introduce retry tokens, range/resume support or unlimited replays as part of this feature.
- [ ] Preserve cleanup of exhausted payloads and readable metadata until normal expiry. Ensure the final allowed in-flight response survives routine exhausted-payload cleanup. Explicit revocation, operator emergency stops and enforced traffic exhaustion cancel work as defined in sections 4 and 6. Verify acknowledgements can still be processed without restoring download allowances.
- [ ] Extend `CreateFileWithQuota` so file-count and byte reservations and file insertion commit atomically. The slot must have room in both budgets, including concurrent uploads into different child transfers. Reject allocation before creating/writing an orphan payload where possible; clean up any temporary artifact on failure.
- [ ] Do not increment the file counter for tus HEAD/PATCH, upload completion, metadata reads or repeated completion notifications. Keep existing upload reservations usable when the remaining allowance reaches zero so those uploads can finish.
- [ ] Retain cumulative reservations after abandonment, child deletion and payload cleanup. Failed transactions that never allocated a file must consume neither count nor byte allowance. Keep operator byte/batch/file-size limits effective regardless of creator settings.
- [ ] Reject new child-transfer creation when the receive file allowance is already exhausted, with the allocation transaction still serving as the final concurrency guard. Keep authorized owner reads, existing-upload resume, accepted-file retrieval and revocation available when only the per-link file allowance is exhausted. Operator suspension and resource emergency limits have the precedence defined in sections 3–6.
- [ ] Ensure guest child-transfer requests cannot override or replenish their parent receive allowance. Do not let anonymous senders introduce a download cap that locks the owner out of retrieving uploaded files.
- [ ] Keep counters persistent across restart and use checked integer operations. Preserve actual-byte traffic accounting for allowed, interrupted and rejected operations without counting reservations as transferred bytes.

## 10. Link creation UX across web, Android and iOS

- [ ] Add a collapsed **Link limits** section to authenticated send creation. Provide an enable control and numeric **Maximum downloads per file** field, with inline validation and help text: “Each started download counts, including interrupted downloads.” Do not apply this owner control to guest uploads through receive links.
- [ ] Add the equivalent optional **Maximum files accepted** field before receive-link creation. Explain that incomplete uploads can use an allowance and that existing server restrictions still apply. Show **Create receive link** as the explicit action.
- [ ] Replace automatic mobile receive-link creation with a compact setup state, preserving optional naming and the existing QR-first result layout. Opening an existing link from History must show that link without creating another one.
- [ ] Capture the selected limit in the same creation request that establishes the transfer/slot. Disable edits once creation/upload begins; preserve the chosen value through recoverable errors without silently reverting to unlimited. Avoid duplicate resource creation on double taps or navigation restoration.
- [ ] Provide equivalent behavior in Android, iOS and the iOS share extension send flow. Keep web/mobile account restrictions and standalone native guest downloads. Receive-inbox reading must use its owner-only flow from section 1, and scanned downloads must apply section 7 preflight safeguards.
- [ ] Keep defaults unset for each genuinely new link; do not silently inherit limits from a previous recipient. Clear drafts appropriately on account/server changes and preserve only the current same-account draft through ordinary UI restoration.
- [ ] Verify numeric keyboards, labels, focus, error announcements, light/dark themes, large text and narrow screens. Keep creation forms compact and prevent settings from reducing the finished QR code's usable area.

## 11. Link limits in recipient, History and detail states

- [ ] Show the chosen limit in generated-link details and owned History/detail views. Receive summaries may read “2 files received · 2 of 5 allowances used”; expose the distinction when incomplete allocations make those numbers differ.
- [ ] Display per-file remaining download attempts on the public download page and native scanned-download detail flow. Recheck metadata after attempts or server errors; counts shown before a click are advisory because another recipient can consume them concurrently.
- [ ] Disable exhausted per-file download actions and show “Download limit reached.” Preserve access to already saved local files; opening or sharing a local copy must not fetch the server again.
- [ ] Make ZIP and native download-all behavior explicit when only some files remain available. Do not start an archive containing unavailable files or silently omit them: offer clearly labelled available-file actions and retain normal all-file behavior when every file is available. Reuse successfully downloaded local data during retries where existing pipelines permit it.
- [ ] Do not report the whole transfer delivered when only a subset was fetched. Preserve existing partial-save checkpoints and acknowledgement rules; an exhausted attempt allowance is not proof of successful delivery.
- [ ] Preflight guest upload selections against the receive allowance, including files added over several picker actions. Handle races gracefully if another uploader consumes capacity after the preflight. Explain whether already allocated uploads can resume and whether a new attempt requires a new link.
- [ ] Show “This link cannot accept more files” on exhausted receive links while retaining owner access to uploaded content. Surface separate messages for byte/batch ceilings rather than pretending the creator's file allowance is exhausted.
- [ ] Keep limits visible without keys/filenames on cross-device owner metadata where appropriate. Do not create parallel history stores or expose secrets to administrators. Preserve standalone send links; new receive-link versioning follows the private-inbox protocol in section 1.

## 12. Verification

- [ ] Add backend contract tests for omitted/zero/positive values, malformed bodies, negative/fractional/oversized values and client attempts to bypass authorization or parent limits.

## Security references and evidence boundary

The findings were derived from this repository's creation/download handlers, quota queries, event subscriptions, request locks, proxy/authentication logic and client crypto/save flows. They were not reproduced by attacking the running server. Validate each remediation against bounded regression cases during implementation.

[OWASP File Upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html) covers hostile uploads, public retrieval and resource limits. [OWASP denial-of-service guidance](https://cheatsheetseries.owasp.org/cheatsheets/Denial_of_Service_Cheat_Sheet.html) informs admission, timeout and resource budgets. [OWASP authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) informs throttling, recent authentication and second-factor controls. [Caddy reverse-proxy documentation](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy) documents its handling of forwarded headers; maintain an explicit application trust boundary rather than assuming every deployment uses the bundled proxy.
